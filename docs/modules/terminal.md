# Terminal

A "Terminal" rail page that opens a login shell as the server's user in a folder you pick: Home, the folder of the session the tab shows, or an absolute path. Output goes to the tab by a long poll, so there is no websocket and no token in an address; input and resize are small POSTs. It is 1 poll for each tab, which carries every terminal the tab shows: a browser gives a host 6 connections, all tabs share them, and the live server is HTTP/1.1, so a poll for each terminal would take them all. The design, with numbers and rules, is [docs/terminal.md](../terminal.md).

- **Owner only.** Every route is the owner's, and each handler checks it too: guests, viewers, and people invited to one session get a 404, and their tabs load no browser module.
- **The shell:** `python3 -I -c <helper> <login shell> <folder> <rows> <cols>`, where the helper is a pty carried in `terminal.ts`. `PI_POCKET_TERMINAL_SHELL` replaces the login shell (tests use it).
- **Environment:** only the allowlist of the design (`HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH`, `LANG`, `LC_*`, `TZ`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`) plus `TERM=xterm-256color` and `COLORTERM=truecolor`. Provider keys, tokens, and Pi Pocket's own variables do not reach the shell.
- **Limits:** 4 shells at once (a 5th start is a 429, also when starts come at once); the last 256 K characters of each are kept in memory; input is at most 32 K characters a POST (413 above). One poll carries up to 16 terminals, each with up to 256 K characters in one answer: the 4 live ones, plus ended ones that still need their last output.
- **Keys are written once.** Each chunk of keys carries the tab and that tab's seq, and the server writes only a seq newer than the last one it took from that tab. It keeps each receipt for 10 minutes after the tab's last write (`PI_POCKET_TERMINAL_RECEIPT_MS`), and never drops one for its number: a repeated seq cannot write twice. 16 tabs may type into one terminal; a 17th is a 429. A POST that failed on the way is sent again with the same chunk and the same seq, after 0.5, 1, 2, and 4 s, while the page says "Input waits for the server…". After 60 s the tab gives up, a request in flight too: it never sends that chunk again by itself, it shows how many characters may not have reached the shell, and **Discard** drops them.
- **A poll carries what the tab received and what its screen drew.** The entry is `id.from.ack`: `from` is the received offset, and `ack` the drawn one, which back pressure follows; a resize goes 1 POST at a time, and a size that changed during one goes right after it. A tab that draws 64 K past the ack of its open poll starts it again, so a paused shell goes on at once.
- **A 409 is a shell that exited.** Its keys and sizes stop, and the tab keeps polling until the answer with its last output and exit code comes. A 404 (or a `gone` entry) ends the terminal.
- **Paste** goes through `term.paste()`, so a shell that asked for bracketed paste gets it, in the same queue as the keys.
- **Back pressure is for each tab:** each poll names the tab that sent it (its id, made once per tab), and a shell pauses its output when the oldest tab still watching it is more than 128 K characters behind; the shell then writes only as fast as its slowest tab. A tab that has not polled for 30 s stops counting, and one shell keeps 16 tabs at most. `PI_POCKET_TERMINAL_TAB_MS` lowers that span; the tests do.
- **When a shell ends:** Close (a `DELETE`), when the shell exits (its code shows for 60 s), 60 s after the last output poll, 60 minutes after the last keystroke, or when the module goes (`web.onDispose` closes every helper's stdin). `PI_POCKET_TERMINAL_DETACH_MS` and `PI_POCKET_TERMINAL_IDLE_MS` lower those 2 spans; the tests do.
- **Nothing is logged.** Keystrokes and output live in memory only; the server log gets a start failure, and nothing else.
- **What the page says:** "Keys typed here go straight to a shell as the server's user. Lancet Guard and Pi do not see them." That is the point of it, and the rule: this is the server's own shell, not a guarded tool call.
- **A phone fits:** a key bar with Esc, Tab, Ctrl (sticky), the arrows, Paste (the clipboard, or a box when the browser says no) and Select (the screen as a text box, for the phone's own copy). The shell keeps running while the page is closed; the rail badge counts it.

Tests: `terminal.test.ts` runs real shells in the Pi Pocket test harness with a temporary `HOME`: input and output, `pwd`, resize by `stty size`, the environment allowlist, the session folder, the cap, `DELETE` and the shell's death, `exit 7`, the detach and idle spans, the module turned off, and the 4 roles. The poll's own rules have tests too: 1 answer for 2 shells, each at its own offset, a `gone` id, and a 400 for a bad list. So do the edges: 6 starts at once give 4 shells and 2 answers of 429; a shell that closed its own fds and runs on still ends with a `DELETE`; a start that is in flight when the module goes spawns nothing; and with 2 tabs on one shell, the slow tab loses no character of 2 MB of output. A repeated seq, and an older one, write nothing into the shell, a receipt older than the tab span still blocks a repeat, a 17th writing tab is a 429, and an expired receipt lets it in. A poll of 16 terminals is answered where 17 are refused, and back pressure follows the ack: a tab that received the output but drew little keeps the shell paused. `terminal-web.test.js` holds the browser module's own small rules to account: the tab's id on a plain-HTTP page, the bounded waits, the 60 s give-up rule (a request that never settles is aborted at the deadline), what a failed request means, the size that is due, and the terminals one poll carries.
